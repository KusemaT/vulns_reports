
## Title

Local File Inclusion via [file] Parameter on [Portfolio] Page

## Vulnerability Type

Local File Inclusion (LFI)

## Summary

[PixelVault] [https://kzlabs.in/subdomains/archive/?file=4.jpg] [file] parameter is vulnerable to local file inclusion.
The application uses user-controlled input from the [file] parameter to build a file path that is then included/read by the server, without properly validating or sanitising it. This allows an attacker to traverse the file system and read arbitrary files on the server, and in some cases (e.g. via log poisoning or PHP wrappers) escalate to remote code execution.

## Vulnerable Endpoint

`https://kzlabs.in/subdomains/archive/?file=4.jpg`

## Steps to Reproduce

1. Navigate to the following URL: `https://kzlabs.in/subdomains/archive/?file=4.jpg`
2. Observe that the contents of the requested file (e.g. `/etc/passwd`) are disclosed in the response instead of the expected page content
3. Repeat with additional target files/wrappers to further demonstrate impact (e.g. application source code, config files, or log files for potential RCE via log poisoning)

## Payload used

`./etc/passwd`

(Other useful payloads to demonstrate impact/bypass: `....//....//....//etc/passwd` for filter bypass, `..%2f..%2f..%2fetc%2fpasswd` URL-encoded, `php://filter/convert.base64-encode/resource=index.php` to read source code, `/var/log/apache2/access.log` combined with User-Agent log poisoning for potential RCE, and a null byte `%00` on older PHP versions to bypass appended extensions)

## Impact

An attacker can perform the following actions using this vulnerability:

- It allows attackers to read arbitrary files on the server, including configuration files, credentials, and application source code
- It can be used to disclose sensitive information such as database connection strings or API keys embedded in config files
- Depending on the environment (e.g. accessible log files, upload functionality, or PHP wrappers), it can be escalated to remote code execution
- It can be used to map out the server's file system and gather information for further attacks
- It can result in a significant loss of confidentiality and, in the worst case, full server compromise

## Recommendations for fix

Ensure user-supplied input is never used to directly construct a file system path. This can be done by:

1. Avoid passing user input to file-inclusion functions altogether; instead use an allow-list that maps a fixed set of valid identifiers to their corresponding file paths server-side
2. If dynamic file access is unavoidable, strictly validate and normalise input, reject any path containing `../`, `..\`, null bytes, or absolute path indicators
3. Run the application in a chrooted or otherwise restricted file system environment to limit which files can be accessed even if traversal occurs
4. Disable dangerous configuration options where applicable (e.g. PHP's `allow_url_include`) and keep the language runtime/framework patched
5. Apply the principle of least privilege to the application's file system permissions so sensitive files cannot be read by the web server process
6. Use a WAF (e.g. Cloudflare) as a defence-in-depth measure, though this should not be relied on as the primary fix
